# OxiBrowser v0.3.0 Design: From HTML Fetcher to Real Headless Browser

> Date: 2025-05-13
> Status: Design Document
> Scope: Bridge the gap between current state and a production-grade headless browser

## Executive Summary

OxiBrowser v0.2.0 is a **well-architected HTML fetcher with JS evaluation**, not yet a complete headless browser. The core architecture (Browser → Session → Page → Frame) is solid, but three critical gaps prevent it from rendering modern websites:

1. **No `window` global** — Most JS libraries assume `window` exists and crash immediately
2. **No DOM mutation** — `document.createElement()` returns `undefined`; SPA pages render as blank
3. **No CSS/Layout** — No visual rendering, no screenshot beyond a blank PNG
4. **Logs pollute stdout** — CLI output is mixed with tracing logs, breaking pipelines

This document proposes a phased roadmap to close these gaps.

## Design: v0.3.0 — "Real Browser APIs"

### Phase 1: `window` Global + DOM Tree Plumbing (P0)

**Goal:** Make `typeof window === 'object'` and `document.createElement` work.

#### 1.1 `window` Global Object

```
File: crates/oxibrowser-core/src/js/runtime.rs (create_context function)

Current state: No `window` global exists
Target: window = globalThis with browser properties

Implementation:
  1. Register `window` as alias for global object:
     context.register_global_property(js_string!("window"), global.clone(), Attribute::all())

  2. Add window properties (getter accessors):
     - window.document → existing document object
     - window.location → { href, hostname, pathname, protocol, origin }
     - window.navigator → { userAgent, language, languages, platform }
     - window.innerWidth / window.innerHeight → config viewport values
     - window.setTimeout/setInterval → existing timer functions
     - window.clearTimeout/clearInterval → existing clear functions
     - window.fetch → existing fetch stub
     - window.console → existing console object
     - window.localStorage → new Storage object
     - window.sessionStorage → new Storage object
     - window.performance → { now() → Date.now() }
     - window.crypto → { getRandomValues() }
     - window.atob / window.btoa → base64 encode/decode

Estimated effort: ~200 lines in runtime.rs
```

#### 1.2 `document.createElement` + DOM Mutation

```
File: crates/oxibrowser-core/src/js/runtime.rs + oxibrowser-webapi

Current state: DOM is read-only snapshot
Target: Full DOM mutation reflecting back to the real Tree

Approach: Bridge JS element objects to Rust DomMutation system

1. document.createElement(tagName):
   - Creates a new element in the DOM tree
   - Returns a JS element object (like create_element_object already does)
   - The element is tracked with a real NodeId in the Tree
   - Mutation is recorded in DomMutation::CreateElement { tag, parent_id }

2. element.appendChild(child):
   - Records DomMutation::AppendChild { parent_id, child_id }
   - JS thread creates a new DomNode in the DomSnapshot map
     (parking_lot::RwLock-protected, no contention since only JS thread writes)
   - Mutation is also recorded for post-eval Rust-side Tree sync

3. element.removeChild(child):
   - Records DomMutation::RemoveChild { parent_id, child_id }
   - Same dual-update pattern

4. document.body / document.head / document.documentElement:
   - Resolve from the DOM snapshot (these exist in the parsed tree)
   - Return JS element objects wrapping real nodes

5. element.innerHTML (write):
   - Parse HTML fragment via html5ever
   - Replace children in the tree

Key challenge: The current DomSnapshot is immutable. We need to support
mutable DOM operations that update both the JS-visible tree AND the
underlying Rust Tree structure.

Architecture choice: Dual-update pattern.
  1. JS thread writes to DomSnapshot immediately (via parking_lot::RwLock,
     safe because only the JS thread writes during eval).
  2. JS thread records DomMutation for each change.
  3. After eval completes, Session::evaluate_js post-processing applies
     the same mutations to the real Rust Tree (already implemented for
     SetAttribute/ClickElement/InputElement).

Estimated effort: ~500 lines
```

#### 1.3 Fix: Logs to stderr

```
File: crates/oxibrowser/src/main.rs

Current: tracing_subscriber::fmt() defaults to stdout
Target: Logs to stderr, only data output on stdout

Fix: tracing_subscriber::fmt().with_writer(std::io::stderr)

This is a 1-line fix but critical for CLI usability.

Estimated effort: 1 line
```

### Phase 2: Real fetch() + Storage (P1)

#### 2.1 Real `fetch()` from JS

```
Current: fetch() returns a stub Response with no real network access
Target: fetch() makes actual HTTP requests via HttpClient

Approach:
  1. Pass an Arc<HttpClient> reference into the JS thread
     (already available in Session, just need to thread it through)

  2. fetch() implementation:
     - Parse URL, method, headers from arguments
     - Send request through a channel to the async runtime
     - Return a Promise that resolves with the response

  Challenge: JS thread is synchronous (std::thread + mpsc).
  fetch() is async by nature.

  Solution: Use oneshot channels
     JS thread sends FetchRequest → async task picks it up →
     sends FetchResponse back through oneshot → JS thread blocks
     on recv() (boa_engine doesn't support async natively)

  This makes fetch() synchronous inside JS (blocking the eval),
  which matches how many SSR/prefetch scripts use it.

Estimated effort: ~300 lines
```

#### 2.2 `localStorage` / `sessionStorage`

```
Current: undefined
Target: Per-origin Storage objects backed by HashMap

Approach:
  1. Storage struct with HashMap<String, String>
  2. Register as JS object with:
     - getItem(key) → string | null
     - setItem(key, value)
     - removeItem(key)
     - clear()
     - length
     - key(index)
  3. localStorage persisted to Browser (shared across sessions)
  4. sessionStorage scoped to Session

  Data flows through a new StorageMutation type (separate from DomMutation
  which is for DOM tree changes):
  StorageMutation::Set { key, value }
  StorageMutation::Remove { key }
  StorageMutation::Clear

  Session::evaluate_js post-processing applies storage mutations to
  the appropriate storage backend (Browser-level for localStorage,
  Session-level for sessionStorage).

Estimated effort: ~200 lines
```

#### 2.3 `window.location`

```
Current: window is not defined
Target: Location object with getters/setters

Approach:
  Register as accessor on window:
  - location.href → current page URL
  - location.hostname → from parsed URL
  - location.pathname → from parsed URL
  - location.origin → scheme + host
  - location.protocol → "https:"
  - location.toString() → href

  Setting location.href triggers DomMutation::Navigate(url)
  which Session::evaluate_js handles by calling self.navigate().

Estimated effort: ~80 lines
```

### Phase 3: Event System + Rendering (P2)

#### 3.1 Real EventTarget

```
Current: addEventListener is a noop
Target: Event listeners fire in response to DOM mutations

Approach:
  1. EventTarget struct: HashMap<event_type, Vec<callback>>
  2. dispatchEvent() invokes registered callbacks
  3. CDP-generated events (DOM.change, Page.loadEventFired) trigger
     corresponding JS event listeners

  This enables frameworks that rely on event delegation.

Estimated effort: ~300 lines
```

#### 3.2 CSS-Based Screenshot

```
Current: Page.captureScreenshot returns a minimal/blank PNG
Target: Text-based visual output (not pixel-perfect Chromium rendering)

Approach (pragmatic):
  1. Use the existing DOM tree to generate a text/terminal "screenshot"
  2. Layout: simple block layout (no flexbox/grid CSS)
  3. Render to an image via the `image` crate (already a dependency)
     - Text nodes → rendered with a bitmap font
     - Background colors → from inline styles
     - Basic box model → width, height, margins

  NOT implementing: full CSS cascade, flexbox, grid, transforms,
  animations, compositing. That's Chromium's job.

  The goal: show visible text content in screenshots, not blank pages.

Estimated effort: ~800 lines (new file: css_layout.rs)
```

### Honest Assessment

After v0.3:
- **Beats Chromium** on: binary size, startup time, memory usage, no C deps
- **Matches Lightpanda** on: architecture, JS engine quality, CDP support
- **Still behind** on: CSS rendering, full Web API coverage, pixel-perfect screenshots

The v0.3 goal is to be the **best Rust-native headless browser** for AI agent workflows where:
- You need DOM parsing + JS evaluation (not pixel rendering)
- You need CDP automation (not visual testing)
- You need fast startup and low memory (not Chrome feature parity)

## Success Criteria (v0.3)

```bash
# 1. window exists
$ oxibrowser eval https://example.com "typeof window"
object

# 2. createElement works
$ oxibrowser eval https://example.com "document.createElement('div').tagName"
DIV

# 3. Clean output (no log pollution)
$ oxibrowser fetch https://example.com --format text
Example Domain
This domain is for use in documentation examples...

# 4. fetch() returns real data
$ oxibrowser eval https://example.com "(async function(){ var r = await fetch('https://httpbin.org/get'); return r.status; })()"
200

# 5. localStorage persists
$ oxibrowser eval https://example.com "localStorage.setItem('key','val'); localStorage.getItem('key')"
val

# 6. SPA rendering works (JS-dependent content visible)
$ oxibrowser fetch https://some-spa-site.com --format markdown
[Shows JS-rendered content, not blank page]
```

## Risks

| Risk | Mitigation |
|------|-----------|
| boa_engine `!Send` limits async fetch() from JS | Use oneshot channel pattern (blocking recv in JS thread). Must increase eval timeout when fetch() is called (default 5s may not suffice for real HTTP requests) |
| DOM mutation in JS thread may be slow | Batch mutations, apply after eval completes |
| Full CSS cascade is infeasible in Rust | Implement only inline styles + basic box model |
| createElement without layout has limited usefulness | Accept that v0.3 is "DOM + JS correct, visuals basic" |

## Not In Scope (v0.3)

- Full CSS cascade / specificity / computed styles
- Flexbox / Grid layout
- WebGL / Canvas 2D rendering
- Audio / Video playback
- Service Workers
- WebAssembly
- DevTools frontend (Elements panel, Console panel, etc.)
- iframe sandbox isolation (security boundary)
